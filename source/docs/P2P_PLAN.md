# P2P 联机规划（仅方案，0.12.0 未实现）

## 目标与边界

先支持一名人工 DM 与少量玩家共享同一战役。DM 主机持有权威状态和完整模组；玩家只接收自己可见的信息。AI 是 DM 的按需工具，不直接接受远端玩家提供的工具名、文件路径或任意状态修改。当前版本仍只监听 127.0.0.1，没有信令、房间、P2P 或公网访问。

## 连接方案

候选是 WebRTC RTCDataChannel。浏览器的数据通道可传输任意应用数据，但 P2P 不等于完全不需要服务：建立连接仍需信令交换；NAT 环境通常需要 STUN，无法直连时要准备 TURN 中继。先做局域网可行性验证，再评估公网信令和中继的费用、运维与隐私。

建议顺序：局域网原型 → 可手动交换邀请信息的试验 → 自建轻量信令 → 可配置的 STUN/TURN。不要依赖没有授权或可靠性保证的公共中继。

依据：[WebRTC Peer connections](https://webrtc.org/getting-started/peer-connections)、[MDN Connectivity](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Connectivity)。

## 权威状态与权限

- 每个房间绑定一个存档 ID；DM 为唯一提交者，玩家拥有其角色的操作权限。
- 客户端发送 intent：requestId、actorId、expectedRevision、动作及目标/坐标。DM 主机校验当前回合、距离、资源及角色归属后执行。
- 提交事件具有 sessionId、递增 seq、eventId、因果 requestId。重复提交返回原回执，过期 revision 要求刷新，不能重掷或二次扣资源。
- DM 全量状态与玩家视图分开投影；隐藏敌人、未探索地图、模组正文、暗骰、DM 私聊、API 密钥都不能进入玩家广播。
- 玩家端不能调用现有本机 HTTP 全量工具接口。联机网关必须使用独立且很小的行动白名单。

## 同步与重连

初次发送经过权限过滤的快照，再按 seq 增量推送事件；客户端确认最后连续序号。断线重连先补缺失事件，超出保留窗口则发送新快照。角色移动先显示待批准预览，收到权威事件后才算生效。

地图文件按内容哈希索引、分块传输，与频繁的小型动作事件分流。限制消息大小和队列，避免大型地图阻塞战斗交互。依据：[MDN Data channels](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Using_data_channels)。

DM 断线时整桌暂停，不在首版自动选举新主机。手动交接必须同时迁移完整存档、事件序列与权限，并吊销旧会话；API 密钥不随存档传给玩家。

## 开发前置工作

1. 把当前 JSON 提交投影进一步整理为统一命令与事件边界，所有变更产生可过滤的事件。
2. 建立 DM/玩家视图投影及测试，证明隐藏信息不会泄漏。
3. 对骰子、结束回合、资源消耗、战役奖励统一幂等键与 revision 校验。
4. 定义协议版本、最大消息体、速率限制、邀请过期和撤销机制。
5. 使用模拟丢包、乱序、重复、重连和主机退出验证，再测试真实 NAT。

## 验收门槛

双人和五人场景分别验证：先攻一致、同一骰子只结算一次、断线后无状态回退、玩家不能控制他人角色、无法读取暗骰或隐藏单位、大地图传输不阻塞交互。公网版本必须有可测的直连成功率与中继费用估算。

这些是后续规划，不代表 0.12.0 已具备联机能力或完整权限隔离。
